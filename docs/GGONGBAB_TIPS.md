# 꽁밥 제보 게시판

소유자 결정(2026-10-31): 레이더가 놓친 오프라인 꽁밥을 방문자가 알려 주는 게시판을 만든다. 제보는 사이트에서 바로 보내고(Supabase), 소유자가 하루 한 번 확인한다. 확인하기 쉽도록 포스터나 현장 사진도 함께 받는다.
소유자 결정(2026-11-01): "사용자는 제보하는거고, 우리는 그거를 분류하는 사람이 되어야". 방문자는 본 것을 한 칸에 자기 말로 적고 사진을 붙이기만 합니다. 행사 이름·장소·날짜·시간·음식은 운영 PC 가 인스타 레이더의 분류 모델로 읽어 채우고, 소유자가 텔레그램에서 확인합니다.
소유자 결정(2026-11-02, "꽁밥 제보는 이제 main에 올려도 될 것 같아"): 운영 사이트에도 올린다. `tip.html` 은 이제 일반 페이지입니다. 모든 페이지의 더보기에 "꽁밥 제보"가 있고, `vercel.json` 이 막지 않습니다. 검색에는 싣지 않습니다(`noindex, nofollow`). 브라우저가 Supabase 를 쓰는 유일한 운영 페이지이며, 쓸 수 있는 것은 아래 "브라우저가 할 수 있는 것"뿐입니다(AGENTS.md 의 예외). 운영 PC 의 검토(`scripts/ggongbab/tips.py`)는 lab 사본에서 돌고, 운영과 lab 의 제보를 함께 받습니다(같은 DB).

## 흐름

1. 방문자가 `tip.html` 에서 본 것을 적어(또는 사진만 붙여) 보냅니다. 브라우저는 `ggongbab_submit_report(...)` 만 부르고, 함수가 검사한 뒤 제보를 저장하고 그 id 를 돌려줍니다. (009 이전 양식의 `ggongbab_submit_tip(...)` 도 그대로 남아 있습니다.)
2. 사진이 있으면 같은 id 의 폴더(`<id>/1.jpg` 등)로 비공개 버킷에 올립니다. 사진이 실패해도 제보는 접수되고, 화면이 "사진은 올라가지 않았어요"라고 알려 줍니다.
3. 운영 PC 가 새 제보(`status = 'new'`)를 읽습니다. 사진은 운영 PC 가 백엔드 키로 직접 내려받습니다.
   - 방문자 글로 온 제보(제목이 비어 있음)는 인스타 레이더의 1차 모델(`OPENAI_MODEL_PRIMARY`, 바꾸지 않음)이 글·사진·오늘 날짜를 보고 행사 이름, 장소, 날짜, 시간, 음식, 꽁밥 여부와 확신도, 애매한 점 한 줄을 정리합니다. 정리한 값은 게시판 한도에 맞춰 잘라 그 제보에 쓰고 `classified_at` 을 남깁니다. 모델이 지어내지 않도록 모르는 값은 비워 두게 합니다. 비용은 인스타 레이더 비용(`analysis_runs`, `tip-<id>`)에 함께 셉니다.
   - 글도 사진도 없는 제보(사진이 끝내 안 올라온 경우)는 묻지 않고 `rejected` 로 둡니다(`TIP_EMPTY_DROPPED`).
   - 모델이 실패해도(`TIP_CLASSIFY_FAILED`) 질문은 갑니다. 칸은 비어 있고 ✏️ 로 채웁니다.
   - 텔레그램 질문: 첫 사진, 방문자 글, "🤖 자동 정리"한 칸들, 판단(꽁밥 같음/아닌 듯, 확신도, 애매한 점), 버튼 ✅ 게시판에 올리기 / ❌ 올리지 않음 / ✏️ 고쳐서 올리기.
4. 소유자가 ✅ 를 누르면(제목·장소·날짜가 다 있을 때만. 없으면 ✏️ 로 채우라고 답합니다) 운영 PC 가 `ggongbab_tip_board` 에 행을 쓰고 제보를 `accepted` 로 바꿉니다. 날짜가 아직 지나지 않았으면 수집함에 `[꽁밥 제보] <제목>` 업무(`제보 ID: <uuid>` 줄 포함)로도 넘겨, 꽁밥 목록에 출처 "제보"로 올라갈 수 있게 합니다. 공개 여부는 파이프라인 규칙이 정합니다. ❌ 는 `rejected` 입니다.
   ✏️ 는 답장용 메시지를 보내고, 소유자가 그 메시지에 "필드: 값" 줄(제목, 장소, 날짜, 시간, 음식)로 답하면 고친 뒤 ✅ 처럼 올립니다. 아직 빠진 칸이 있으면 무엇이 빠졌는지 답하고 같은 메시지에 다시 답장하면 됩니다.
5. 게시판은 확인된 제보만 보여 줍니다. 다가오는 것을 가까운 날짜부터, 그다음 지난 2주를 최근 날짜부터 보여 줍니다.

3·4단계(텔레그램 확인, 게시판 쓰기, 수집함 넘기기, 사진 정리)는 운영 PC 의 `scripts/ggongbab/tips.py` 가 합니다. 인스타 레이더의 텔레그램 봇을 함께 씁니다(봇 하나에 업데이트를 읽는 프로세스는 하나). 새 제보는 들어오고 2분 뒤(사진 업로드가 끝난 뒤) 한 번만 묻고, 확인은 소유자가 편할 때 합니다. 이 문서의 표와 권한이 그 계약이고, 시험은 `tests/ggongbab/test_tips.py` 입니다.
운영 PC 는 `lab` 체크아웃에서 돌므로 `scripts/ggongbab/tips.py` 와 그 시험은 `lab` 브랜치에만 있습니다. `main` 에는 사이트 쪽(페이지, 함수 SQL, 그 시험)만 있습니다.

## 표와 버킷

| 이름 | 내용 | 브라우저 |
|------|------|----------|
| `ggongbab_tips` | 제보: 행사 이름(2~80자), 장소(1~80자), 날짜, 시간(40자), 음식·경품(120자), 자세히(1000자, 방문자 글), 링크(선택, `http(s)://`, 300자), `image_count`, `client_hash`, `status`(`new`·`accepted`·`rejected`), `notified_at`, `reviewed_at`, `dooray_post_id`, `classified_at`(009: 운영 PC 모델이 칸을 채운 시각). 009 부터 행사 이름·장소·날짜는 비어 있을 수 있습니다(방문자 글 제보) | 못 봄, 못 씀 |
| `ggongbab_tip_board` | 게시판: 확인된 제보의 행사 이름, 장소, 날짜, 시간, 음식, `accepted_at`. 같은 id, 제보가 지워지면 함께 지워짐 | 읽기만 |
| `ggongbab_tip_rate` | 남용 제한: (주소+한국 날짜+비밀 소금)의 해시, 시간 창, 제보 수. 하루 지나면 지움 | 못 봄 |
| `ggongbab_tip_secret` | 해시 소금 | 못 봄 |
| 버킷 `ggongbab-tip-images` | 비공개. JPEG·PNG·WebP, 장당 5MB | 올리기만(아래 조건) |

- 게시판에는 자세히·링크·사진·보낸 사람에 관한 값이 없습니다. 원본 포스터는 공개 사이트에 다시 싣지 않습니다.
- `image_count` 는 0 으로 둡니다. 사진 수는 운영 PC 가 버킷에서 셉니다.
- 백엔드 키(`service_role`)는 제보를 읽고 상태를 바꾸며, 게시판과 버킷을 모두 다룹니다.

## 브라우저가 할 수 있는 것

- `ggongbab_submit_report(p_text, p_photos, p_hp)` → 새 제보 id(uuid). 009, 지금 페이지가 쓰는 함수입니다.
  - 글은 앞뒤 공백을 지운 뒤 1000자까지, `p_photos`(올릴 사진 수)는 0~3 입니다. 글이 2자 이상이거나 사진이 1장 이상이어야 합니다. 어긋나면 `TIP_INVALID` 입니다.
  - 허니팟과 남용 제한(주소 해시, 한 시간 5건, 전체 24시간 60건)은 아래 `ggongbab_submit_tip` 과 글자 하나 다르지 않게 같습니다.
  - 글은 `details` 에만 들어가고, 행사 칸은 비워 둡니다. 운영 PC 가 채웁니다.
- `ggongbab_submit_tip(p_title, p_place, p_event_date, p_time_text, p_food, p_details, p_link, p_hp)` → 새 제보 id(uuid). 008, 예전 양식용으로 남겨 둡니다.
  - 앞뒤 공백을 지운 뒤 길이와 날짜(한국 날짜로 어제부터 60일 뒤까지), 링크를 검사합니다. 어긋나면 `TIP_INVALID` 입니다.
  - 같은 주소에서 한 시간에 6번째 제보, 또는 24시간 동안 전체 60건을 넘으면 `TIP_RATE_LIMITED` 입니다.
  - `p_hp` 는 사람에게 보이지 않는 칸(허니팟)입니다. 값이 있으면 봇으로 보고 아무것도 저장하지 않은 채 임의의 id 를 돌려줍니다. 봇은 차이를 알 수 없습니다.
- 사진 올리기(`storage.objects` INSERT 만): 경로가 `<제보 id>/<1|2|3>.<jpg|png|webp>` 이고, 그 제보가 `new` 이며 15분 안에 보낸 것이고, 폴더에 사진이 3장 미만일 때만 됩니다. 덮어쓰기, 읽기, 목록, 지우기, 공개 주소는 모두 안 됩니다. 검사는 `ggongbab_tip_upload_allowed(name)` 이 합니다.
- `ggongbab_tip_board` 읽기.

## 화면 (`tip.html`, `css/tip.css`, `js/ggongbab-tips.js`)

- 머리: "모르는 꽁밥, 알려 주세요"(본 그대로 알려 주면 정리는 운영자가), 확인은 하루 한 번 · 확인된 제보만 공개 · 사진·세부 내용은 비공개, 제보 예시 티켓(장식).
- 순서 세 칸(제보 → 운영자가 정리·확인 → 게시판 공개), 받는 제보와 빼 줄 것(개인정보, 대학원생 전용, 온라인 참여만 하는 추첨, 판매·할인).
- 제보 칸(2026-11-01 부터): "어떤 꽁밥인가요?" 한 칸(1000자, 글자 수, 예시 문장)과 사진(최대 3장, 미리보기와 빼기 버튼)뿐입니다. 포스터 사진만 올려도 됩니다. 2000px 보다 크거나 5MB 를 넘는 사진은 브라우저에서 긴 변 2000px JPEG 로 줄여 올립니다.
- 글도 사진도 없으면 보내지 않고 이유를 적은 뒤(`aria-invalid`) 그 칸으로 초점을 옮깁니다. 상태는 `role="status"` 로 읽힙니다. 글을 쓰거나 사진을 붙이면 표시가 바로 사라집니다. 사진만 보낸 제보에서 사진이 하나도 안 올라가면 "제보가 비어 있어요"라고 알려 다시 보내게 합니다.
- 공개 설정(`js/ggongbab-public-config.js`)이 비었거나 클라이언트를 불러오지 못하면 제보 칸이 닫히고 "지금은 제보를 받을 수 없어요", 게시판은 "게시판을 불러오지 못했어요"라고 말합니다. 이때 페이지는 아무 요청도 하지 않습니다.
- Supabase 클라이언트는 공개 피드와 같은 고정 버전(`@supabase/supabase-js@2.116.0`, integrity 포함)입니다.
- 진입: 모든 페이지 더보기의 "꽁밥 제보"(`shared/nav.html`, 2026-11-02), `lab.html` 의 버튼, `lab-ggongbab.html` 의 "꽁밥 제보하기".

1. Supabase 대시보드 → SQL Editor 에서 `supabase/migrations/008_ggongbab_tips.sql` 내용을 붙여 넣고 실행합니다(006 다음이면 되고, 007과는 순서가 상관없습니다). 버킷과 사진 정책도 이 파일이 만듭니다.
2. 확인: Storage 에 `ggongbab-tip-images` 가 **Private** 로 보이고, Table Editor 에 `ggongbab_tips`·`ggongbab_tip_board` 가 RLS 켜짐으로 보이면 됩니다.

4. 방문자 글 양식(2026-11-01): 같은 SQL Editor 에서 `supabase/migrations/009_ggongbab_tip_reports.sql` 을 실행합니다(008 다음). 브라우저 권한은 넓히지 않고 함수 하나만 더합니다. **새 페이지를 lab 에 올리기 전에 실행해야** 제보가 들어옵니다. 확인: Database → Functions 에 `ggongbab_submit_report` 가 보이고, `ggongbab_tips` 에 `classified_at` 열이 생기면 됩니다.
