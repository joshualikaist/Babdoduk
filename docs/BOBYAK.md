# 밥약 메이커 (밥도둑 2.0 Phase 3, lab 전용)

소유자가 확정한 밥도둑 2.0 요구사항(2026-11-08, Q3·Q4·Q5·Q8–Q12·Q17·Q27·Q32)의 셋째 단계입니다. 소유자는 2026-11-08에 착수를 승인했습니다("2,3 단계도 승인해줄게").
이 페이지에는 식당 뽑기(룰렛), 식당 정보 카드, 먹킷리스트, 정산이 있습니다. 설계는 [BABDODUK_2_PLAN.md](BABDODUK_2_PLAN.md)의 "3단계"에 있습니다.

**상태:** lab 작업 브랜치 `agent/claude/bobyak`에 있습니다. `bobyak.html`과 `data/places/`는 **실험실 전용**이어서, babdoduk-lab이 아닌 모든 주소에서는 `vercel.json`이 404로 답합니다.
들어가는 길은 `lab.html`의 "밥약 메이커 (실험실 전용)" 버튼 하나입니다. 공개 내비는 바꾸지 않았습니다. 내비를 2.0의 네 메뉴로 바꾸는 일은 소유자의 결정을 기다리고 있습니다.
다음 일은 아직 하지 않았습니다.
- lab 배포
- 실기기 확인
- 실제 식당 데이터 수집. 공공데이터 키가 아직 없습니다.
- 마이그레이션 012 적용
- main 반영

## 정산 규칙 (`js/bob-settle.js`)

* 금액은 정수 원입니다. 총액은 0원부터 1억 원까지 넣을 수 있습니다. "45,000원"처럼 쉼표와 "원"이 붙어도 읽고, 소수나 음수는 오류로 처리합니다.
* **나눠 내기**에서는 먼저 "직접 정한 금액"을 뺍니다. 남은 돈은 제외하지 않았고 금액도 정하지 않은 사람들이 똑같이 나눕니다.
  - 한 사람 몫은 고른 단위로 **내림**합니다.
  - 남는 단위는 목록 **위쪽 사람부터 한 단위씩** 더 냅니다.
  - 총액이 단위로 나누어떨어지지 않으면, 한 단위가 안 되는 나머지는 첫 사람이 냅니다.
  - 그래서 몫의 합은 **항상 총액과 같습니다**. 코드가 계산 뒤에 합을 다시 확인합니다.
  - 예: 10,000원을 3명이 1원 단위로 나누면 3,334 / 3,333 / 3,333원입니다. 100원 단위면 3,400 / 3,300 / 3,300원입니다.
* **한턱**: 고른 한 사람이 총액을 내고, 나머지는 0원입니다. 이 방식에서는 제외와 직접 정한 금액을 쓰지 않습니다.
* 아래 경우는 조용히 고치지 않고, 무엇이 문제인지 말합니다.

  | 경우 | 오류 |
  |---|---|
  | 정산할 사람이 없음(전원 제외) | `nobody` |
  | 31명 이상 | `tooMany` |
  | 총액이 범위 밖 | `total` |
  | 직접 정한 금액의 합이 총액보다 큼 | `fixedOver` |
  | 모두 금액을 정했는데 합이 총액과 다름 | `fixedShort` |
  | 금액이 숫자가 아님 | `fixedInvalid` |
  | 한턱인데 낼 사람이 없음 | `payer` |

## 데이터 (`data/places/latest.json`, 계약 `schemas/places-feed.schema.json`)

```json
{"schemaVersion": 1, "updatedAt": "2026-11-08" | null,
 "source": {"name": "소상공인시장진흥공단 상가(상권)정보", "url": "https://www.data.go.kr/data/15012005/openapi.do", "terms": "…"},
 "places": [{"id": "p-0001", "name": "…", "branch"?: "…", "nameEn"?: "…", "area": "kaist|eoeun|gung",
             "address": "도로명주소", "lat"?: 36.36, "lng"?: 127.36, "cuisine": "korean|…|other",
             "status": "verified|candidate|stale|closed", "verifiedAt": "YYYY-MM-DD" | null,
             "facts": [{"kind": "budget|menu|hours|closedDay|phone|note", "text": "…", "textEn"?: "…",
                        "band"?: "under10k|10to15k|over15k", "source": "operator|official|public-data|tip",
                        "url"?: "https://…", "checkedAt": "YYYY-MM-DD"}],
             "sources": [{"kind": "semas", "ref": "<상가업소번호>", "checkedAt": "YYYY-MM-DD"}],
             "updatedAt": "YYYY-MM-DD"}]}
```

* **처음 파일은 비어 있습니다**(`places: []`). 운영자가 확인한 식당이 아직 없고, 식당을 지어내지 않기 때문입니다. 페이지는 "아직 올라온 식당이 없어요. 밥도둑이 직접 확인한 식당부터 차례로 올라와요"라고 씁니다. 파일을 읽지 못하면 "불러오지 못했어요"와 다시 불러오기를 보여 주어, 빈 것과 실패를 구분합니다.
* **id**는 사이트가 붙이는 번호(`p-0001`부터)입니다. 공공데이터의 상가업소번호와는 따로 두고, 그 번호는 `sources`에 남깁니다. 공공데이터 측은 상권업종분류를 개편하면서 상가업소번호를 새로 만들어 이전 번호와 이어지지 않는다고 안내한 적이 있습니다(검색 결과로 본 안내라 날짜는 확인하지 못함). 그래도 사이트 id와 공유 링크, 먹킷리스트는 그대로 유지됩니다.
* **검증 상태**는 다음 넷입니다.

  | 상태 | 뜻 |
  |---|---|
  | `verified` | 운영자가 직접 확인함(`verifiedAt` 필수) |
  | `candidate` | 공공데이터에만 있음. 사실(`facts`)이 없고, `verifiedAt`은 null |
  | `stale` | 폐업이나 변경이 의심됨 |
  | `closed` | 폐업 |
* 사실 하나하나에 출처와 확인 날짜가 붙습니다. 예산 사실에는 `band`가 필요하고, 다른 사실에는 붙이지 않습니다.
* 검사 규칙: `scripts/validate_content.py --only authored`가 계약을 확인하고, 그 밖의 규칙은 `scripts/places/semas.py` `feed_rule_errors`가 봅니다.
  - id 중복과 같은 상가업소번호의 중복 공개가 없어야 합니다.
  - 확인된 식당에는 날짜가 있어야 합니다.
  - 후보에는 사실이 없어야 합니다.
  - 사실 규칙을 지켜야 합니다.

## 운영 절차 (`scripts/places/semas.py`)

키는 환경변수 `DATA_GO_KR_KEY`, 또는 `~/.config/babdoduk/credentials`에서 읽습니다. 이것이 파일이면 그 안의 `DATA_GO_KR_KEY=` 줄을, 운영 PC처럼 폴더이면 그 안의 `data-go-kr` 파일(키 한 줄, 또는 `DATA_GO_KR_KEY=` 줄)을 읽습니다. 화면, 로그, 파일 어디에도 키를 출력하지 않습니다. `key` 명령은 "set" 또는 "not set"만 알려 줍니다.

```
python scripts/places/semas.py key       # 키가 있는지만
python scripts/places/semas.py fetch     # 공공데이터 → inputs/places/candidates.json (배포 안 됨)
python scripts/places/semas.py review    # 공개 파일과 비교 → inputs/places/review.json, approvals.json에 결정 칸 추가
#  (운영자가 inputs/places/approvals.json의 decision 칸을 채움)
python scripts/places/semas.py publish   # 결정만 반영 → data/places/latest.json (계약 검사 통과해야 씀)
```

1. **fetch**는 다음 사각형 하나에서 식당을 받습니다.
   - 사각형: 경도 127.338–127.376, 위도 36.352–36.382. KAIST 본원, 어은동, 궁동을 덮습니다.
   - 남기는 조건: 상권업종 대분류가 "음식"이고, 대전 유성구 법정동이 **구성동**(KAIST 교내로 봄)·**어은동**·**궁동**인 곳입니다.
   - 음식 종류는 중·소분류 이름으로 정합니다(`CUISINE_RULES`).
   - 2만 건이 넘으면 일부만 믿지 않도록 멈춥니다. 키가 없으면 요청 없이 멈춥니다.
2. **review**는 새 가게, 공공데이터에서 사라진 가게(폐업 의심), 이름·주소가 바뀐 가게를 찾습니다. 각각을 결정이 비어 있는 행으로 `approvals.json`에 더합니다. 이미 적은 결정은 건드리지 않습니다.
3. 운영자는 `decision` 칸을 채웁니다. 빈 칸은 "아직 안 정함"이고, 그 행에는 아무 일도 일어나지 않습니다.

   | 행 | 고를 수 있는 결정 |
   |---|---|
   | `new` | `verified`(직접 확인함: `checkedAt` 필수, `facts`에 확인한 것만), `candidate`(후보로 공개), `skip` |
   | `missing` | `stale`, `closed`, `keep` |
   | `changed` | `accept`, `keep` |

   이미 공개한 후보를 나중에 확인하면 `{"kind": "promote", "id": "p-0007", "decision": "verified", "checkedAt": …, "facts": […]}` 행을 손으로 더합니다.
4. **publish**는 결정된 행만 반영합니다. 같은 결정으로 다시 돌려도 바뀌는 것이 없습니다. 맞지 않는 결정이 하나라도 있으면 파일을 쓰지 않고 멈춥니다. 예: 날짜 없는 `verified`, `band` 없는 예산, 출처 없는 사실, 공개되지 않은 가게에 `closed`.
5. 공개 파일은 일반 커밋으로 lab에 올립니다(생성 데이터 봇과 무관). 정기 실행은 GitHub Actions에 넣지 않았습니다. 지금은 운영자가 한 달에 한 번쯤 위 명령을 돌리는 것으로 충분합니다. 자동화하려면 워크플로 변경 승인이 따로 필요합니다.

## 먹킷리스트 저장 형식 (localStorage)

| 키 | 값 |
|---|---|
| `babdoduk-places-saved` | `{"v":1,"items":[{"id","status":"want|been|again","memo","savedAt","updatedAt"}]}` (최대 500개, 최근 것이 앞, 메모 500자) |
| `babdoduk-places-saved-unreadable` | 읽을 수 없던 원래 값의 사본(한 번만). 목록은 "새로 시작했어요"라고 알립니다. |

* 이 브라우저에만 있습니다. 칸의 뜻은 2단계 마이그레이션 011의 `saved_places(place_id, status, memo, saved_at, updated_at)`과 같아서, 로그인 동기화가 그대로 옮길 수 있습니다.
* 형식이 깨졌으면 사본을 남기고 빈 목록으로 시작합니다. 이 페이지보다 새 버전(`v` > 1)이면 보여 주기만 하고 다시 쓰지 않습니다. 저장이 안 되는 브라우저에서는 "이 브라우저에서는 저장할 수 없어요"라고 알립니다.

## 제보 (Q9)

`supabase/migrations/012_place_reports.sql`은 **초안이며 적용하지 않았습니다**. 소유자 승인(Q30) 뒤 SQL 편집기에서 손으로 적용합니다. 008의 소금(salt) 표를 쓰므로 008 다음에 적용해야 합니다.

* 브라우저는 확인 함수 `place_submit_report(p_place_id, p_kind, p_details, p_hp)` 하나만 부를 수 있습니다.
  - `kind`는 `wrong`, `closed`, `new`, `tip` 중 하나입니다.
  - 내용은 2–600자입니다.
  - 미끼 칸(honeypot)이 채워지면 저장하지 않습니다.
  - 남용 제한: 한 사람(주소와 날짜의 소금 해시)당 한 시간에 5건, 전체 하루 100건입니다.
* 두 표(`place_reports`, `place_report_rate`)는 RLS가 켜져 있습니다. 공개 역할(anon, authenticated)에는 아무 권한도 없고, 공개 게시판도 없습니다. 운영자만 백엔드 키로 읽습니다.
* 제보는 운영자가 확인한 뒤 위 approvals 절차로만 반영됩니다. 공개 평점·리뷰는 없습니다.
* 지금은 어느 페이지도 이 함수를 부르지 않습니다. 시험 `test_no_page_calls_the_place_report_function_yet`이 이를 확인합니다. 제보 양식은 012를 적용한 뒤 별도 작업으로 붙입니다. main에서 공개 설정(`js/ggongbab-public-config.js`)을 부를 수 있는 페이지는 tip.html뿐이라는 규칙(AGENTS.md)도 그때 함께 바꿔야 합니다.
