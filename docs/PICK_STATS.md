# 오늘 뭐 먹지: 모두의 취향 (lab 전용)

소유자 결정(2026-11-05): 뽑기에 나오는 배달 메뉴가 "한국 정서와 조금 다른 것 같다"는 데서 시작해, 학생들 취향을 알아내는 방법 중 **A**("결과 카드에 👍 이거 먹을래요, 다시 뽑기는 '별로'로 보고 메뉴별 합계만 모아 많이 고른 메뉴가 더 자주 나오게")를 골랐다("방법 A가 맞는 것 같아").

**lab 전용**이다. `main` 의 페이지 중 Supabase 설정(`js/ggongbab-public-config.js`)을 읽는 것은 꽁밥 제보(`tip.html`)뿐이라(AGENTS.md), `choose.html` 이 같은 설정을 읽으려면 소유자가 그 예외를 따로 허락해야 한다. 그 전까지 운영 후보에는 이 기능의 커밋을 넣지 않는다. 설정이 없으면 페이지는 인기도로만 뽑고 👍 버튼도 보이지 않는다.

## 무엇을 모으나

| 표 | 내용 | 브라우저 |
|----|------|----------|
| `pick_dish_stats` | 메뉴마다 뽑힌 수(`draws`), 👍 수(`likes`), 👍 없이 다시 뽑은 수(`rerolls`) | 읽기만 |
| `pick_rate` | 남용 제한: (주소+날짜+비밀 소금)의 해시, 시간 창, 신호 수. 하루 지나면 지움 | 못 봄 |
| `pick_secret` | 해시 소금 | 못 봄 |

- 사람·뽑기마다의 기록은 남기지 않고 **합계만** 늘린다. 이름, 계정, 자유 입력은 없다. 학식은 보내지 않는다(배달 메뉴만).
- 브라우저는 표에 직접 쓸 수 없다. `pick_record(p_dish, p_signal)` 하나만 부를 수 있고, 함수가 신호(`draw`·`like`·`reroll`), 메뉴(`pick_dish_stats` 에 있는 행), 한 시간 120번 제한(`PICK_RATE_LIMITED`)을 확인한 뒤 그 메뉴의 그 합계를 1 올린다.
- 페이지(`js/pick.js`)가 보내는 때:
  - `draw`: 기계가 배달 메뉴를 뽑았을 때
  - `like`: 결과 카드의 **👍 이거 먹을래요** 를 눌렀을 때(뽑기마다 한 번, 누르면 "👍 좋아요! 다음 뽑기에 반영할게요")
  - `reroll`: 👍 없이 그 메뉴에서 **다시 뽑기** 를 눌렀을 때(한 번)

## 뽑기에 쓰는 법

메뉴의 무게 = 인기도 × `taste(likes, rerolls)` = 인기도 × 2 × (likes + 2) / (likes + rerolls + 4).

- 표가 없으면 1(인기도 그대로). 👍 가 쌓이면 2 쪽으로, 다시 뽑기가 쌓이면 0 쪽으로 간다.
- +2/+4 는 "👍 두 번, 다시 뽑기 두 번"을 미리 둔 것이라 몇 표로는 조금만 움직인다(👍 10번이면 1.71, 다시 뽑기 10번이면 0.29).
- 👍 가 3번 이상인 메뉴는 카드에 "👍 N명이 이걸 골랐어요" 를 보인다.
- 합계는 페이지를 열 때 한 번 읽는다. 읽기나 보내기가 실패해도 뽑기는 그대로 된다.

## 적용 (소유자, 한 번)

1. Supabase 대시보드 → SQL Editor 에서 `supabase/migrations/010_pick_stats.sql` 내용을 붙여 넣고 실행한다(009 다음).
2. 메뉴를 넣는다(백엔드 키, 운영 사본 `.env`): `python scripts/pick_stats.py seed` → `pool N | counted dishes N | pool dishes missing 0`
3. 확인: `python scripts/pick_stats.py check` → `counted dishes N | draws … | likes … | rerolls … | pool N`
4. 뽑기 메뉴가 바뀌면(`scripts/page_content.py` `pick_pool`) 2를 다시 실행한다. 이미 있는 메뉴의 합계는 바뀌지 않는다.

적용 전에도 lab 페이지는 정상이다: 읽기는 실패로 넘어가고(인기도로만 뽑음) 보내기는 무시된다.
